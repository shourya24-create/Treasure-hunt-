## 1. High-Level Architecture & Overview

### Overall picture (from spec — not yet implemented)

The spec describes a **two-app, one-origin, browser-only system** built on a single Firebase project:

| Layer | Technology | Hosted at |
|---|---|---|
| **Team / Admin App** | Flutter Web | `hosting/` → root `/` |
| **Field AR App** | Vite + Three.js + MindAR.js | `hosting/field/` → `/field/` |
| **Backend Logic** | Cloud Functions (TypeScript) | Firebase Functions v2 |
| **Database** | Firestore | Firebase project `treasure-hunt-38935` |
| **Auth** | Firebase Anonymous + Email/Password | Firebase Auth |
| **Assets** | Hosting static files | `/field/targets/`, `/field/audio/` |

### How the four pillars are stitched together

```
Phone Browser
┌─────────────────────────────────────────────────────────┐
│   Flutter Web (/)          Field App (/field/)           │
│   ┌──────────────┐         ┌──────────────────────────┐ │
│   │ Login/Scan/  │ launchUrl│ index.html               │ │
│   │ Journal/Admin│──────────▶ main.js (boot)           │ │
│   │ (Dart/HTML)  │         │  ├── arSession.js         │ │
│   └──────────────┘         │  │   └─ MindARThree       │ │
│          │                 │  │       (camera+marker)  │ │
│          │ shared anon     │  ├── fragmentLoader.js     │ │
│          │ Firebase session│  └── fragmentNN.js ──────▶ │ │
│          │ (same origin)   │       Three.js scene       │ │
│          ▼                 └──────────────────────────┘ │
│   Firebase SDK (JS/Dart)                                 │
│   Firestore ◀── Real-time streams ──▶ both apps         │
│   Cloud Functions ◀── Callable RPCs (submit, join, etc.)│
└─────────────────────────────────────────────────────────┘
```

**Key architectural decisions:**
- **Same origin** is non-negotiable — it lets an anonymous Firebase session created in Flutter be reused by the MindAR app without a second sign-in.
- **Flutter does not embed Three.js** — they are separate pages linked by `launchUrl`. The apps share state only through Firestore.
- **All answer grading lives on the server** (Cloud Functions `submitAnswer`). The field app contains display labels only.
- The spec explicitly drops Unity, AR Foundation, and native Quest.

## 4. Feasibility & Risk Audit

### R1 — Flutter Web ↔ Field App Integration
**Risk level: LOW (by design)**

The spec deliberately avoids the Flutter-embeds-WebGL problem by using `launchUrl(..., webOnlyWindowName: '_self')`. There is no `HtmlElementView`, no iframe. The apps share state only through Firestore, which is clean.

**Remaining risk:** On iOS Safari, `launchUrl` with `_self` behaves differently from Android Chrome. The `authStateReady()` call in `firebaseClient.js` should handle session restoration, but needs explicit testing.

### R2 — Shared Anonymous Session (same-origin requirement)
**Risk level: MEDIUM**

The architecture's correctness depends entirely on both apps using:
- The same Firebase project (`treasure-hunt-38935` is confirmed)
- The same `apiKey`
- The same default app name (`[DEFAULT]`)
- Served from the **same origin** (currently not enforced — `public/` is the wrong field app)

If any of these differ, teams fail membership checks with a confusing silent error.

### R3 — MindAR Performance on Mobile Browsers
**Risk level: HIGH**

| Issue | Severity | Mitigation in spec |
|---|---|---|
| Target compilation 2–10s on mid-range Android | High | None — no loading spinner specified |
| iOS Safari memory pressure with Three.js + camera | High | `renderer.dispose()` called in `ArSession.stop()` ✅ |
| `getUserMedia` on HTTP origins blocked | Critical | Firebase Hosting is always HTTPS ✅ |
| Multiple Three.js instances from mixed imports | Medium | See G11 |
| Tracker drops frames below Snapdragon 730 | Medium | Manual fallback path exists ✅ |
| Safari 15 and below: no `OffscreenCanvas` | Medium | None |

### R4 — DOM Overlay vs. Three.js Canvas Z-ordering
**Risk level: LOW (architecture handles it)**

`#ar-container` for MindAR canvas/video and `#dom-overlay` as a separate `position: fixed` div on top. Touch events work on DOM layer normally. `field.css` must set z-indices correctly.

### R5 — Race Conditions in Fragment Progression
**Risk level: LOW (gate pattern is solid)**

`FragmentLoader` uses `inflight` + `gate` + `queue` to serialize progression. Well-designed.

**One edge case:** Network drop mid-submit leaves `inflight` hanging indefinitely — add a `Promise.race` with a 10s timeout.

### R6 — Firestore Security Rule Gap (admin team read)
**Risk level: MEDIUM**

`watchAllTeams()` reads the `teams` collection root. The spec's rules only grant read on `teams/{teamId}` for members/facilitators — no wildcard collection-level read for facilitators. Will throw `permission-denied` for the dashboard.

**Current status:** Currently masked because `firebase.rules` allows any authenticated read — will surface immediately when spec rules are deployed (N1).

### R7 — No Run Timer
**Risk level: HIGH (vs. initial plan)**

Zero timer implementation in schema, functions, or UI. The core loop of "solve before time expires" is completely absent. Must be designed and built.

### R8 — WebAR Mobile Browser Compatibility Matrix

| Browser | AR likely works | Known issues |
|---|---|---|
| Chrome Android 90+ | ✅ | None with HTTPS |
| Safari iOS 15+ | ⚠️ | `getUserMedia` may prompt twice; PWA mode can break camera |
| Safari iOS 14 | ❌ | `WebAssembly.instantiateStreaming` blocked |
| Samsung Internet | ⚠️ | `OffscreenCanvas` support varies |
| Firefox Android | ⚠️ | Works but slower than Chrome |
| In-app browsers (Instagram, WhatsApp) | ❌ | `getUserMedia` blocked by default |

No browser compatibility nag screen in spec or project.
